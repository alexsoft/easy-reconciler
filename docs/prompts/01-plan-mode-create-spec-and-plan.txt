⏺ Q3 — Match/allocation data model: one table or two?

  This is the schema decision that everything else hangs off. Three options:

  (A) Single allocations table. One row per (transaction, invoice) link with
  amount, confidence, status (proposed / confirmed / rejected), source (auto /
  manual), created_by. Re-running the matcher updates rows in place keyed on
  (txn_id, invoice_id). Simple. Audit log is a separate append-only table that
  records every status transition.

  (B) Two tables: match_proposals (matcher output, ephemeral) + allocations
  (confirmed truth). The matcher writes proposals; reviewer actions promote a
  proposal into an allocation. Cleaner separation — proposals can be wiped and
  recomputed without touching truth — but you maintain two schemas and reconcile
   between them.

  (C) Single allocations table + a separate transaction_matches view for the
  matcher's working set. Hybrid: same as (A) but the matcher reads/writes
  through a thin abstraction so you could swap proposal storage later.

  My recommendation is (A) — for a 4–6h scope it gives you idempotency (upsert
  by (txn_id, invoice_id)), a clean audit trail, and avoids the two-table sync
  problem. The status field already encodes the proposed-vs-confirmed
  distinction (B) is reaching for. The downside — that re-running the matcher
  could overwrite a human-confirmed allocation — is solved by the rule "matcher
  only touches rows where status = 'proposed'."

⏺ Design — section 3 of 5: Matcher pipeline

  Shape: a pure function runMatcher(db) → MatcherReport that's idempotent. It
  runs as the last step of seed, on demand via POST /api/matcher/run, and the
  report is shown as a toast in the UI. Each rule is a separate file under
  src/matcher/rules/ exporting (ctx) => Proposal[]. The pipeline runs them in
  order; once a transaction has a confirmed allocation OR is unrelated, it's
  skipped entirely.

  Confidence buckets (drives auto-confirm vs. needs-review):
  - >= 0.95 → auto-confirm: matcher writes the allocation as status:
  'confirmed', source: 'auto', txn → auto_matched (or partially_allocated if
  amount < invoice balance).
  - 0.70 – 0.94 → propose: status: 'proposed', txn → needs_review. Reviewer
  confirms with one click.
  - < 0.70 → no proposal written; txn stays unmatched.

  Rules in order (first one to score ≥ 0.70 wins for that txn):

  R1 — Exact structured reference (confidence 1.00)
  - transactions.structured_reference exact-equals an invoices.id, currency
  matches.
  - Amount equals invoice total → confirmed full payment.
  - Amount < invoice total within tolerance → confirmed partial (txn
  partially_allocated).
  - Amount > invoice total → confirmed up to invoice total, remainder flagged
  for review (overpayment).

  R2 — Reference extracted from description (confidence 0.95)
  - Regex /INV-\d{4}-\d{4}/ against description. Same amount logic as R1.

  R3 — Fuzzy reference (confidence 0.85)
  - structured_reference or description contains a token that's
  Levenshtein-distance ≤ 2 from a known invoice id, OR matches the id with
  separators stripped (INV20260003 ≈ INV-2026-0003). Amount must match within
  tolerance.

  R4 — Customer name + amount + date window (confidence 0.80)
  - Normalize counterparty_name (lowercase, strip suffixes S.à r.l. / SARL /
  S.A. / SCS / SARL-S, strip whitespace and punctuation, strip IBAN LU… tail).
  - Compute Jaro-Winkler similarity against normalized invoices.customer_name.
  Threshold 0.88.
  - Among customer matches: amount equals an open invoice's balance, date within
   issue_date − 7 days .. issue_date + 60 days. Single hit → propose.

  R5 — Consolidated payment (subset-sum) (confidence 0.75)
  - Same customer match as R4. Find a subset of that customer's open invoices
  whose balances sum to the txn amount (±1 cent tolerance). Bounded: max 5
  invoices, max 64 candidates considered (small DP). Single subset → propose
  multi-row allocation. Multiple valid subsets → no proposal, txn stays
  unmatched (reviewer disambiguates).

  R6 — Credit-note netting (confidence 0.80)
  - Run after R1–R5. For each open credit note, find an open invoice for the
  same customer whose balance equals the credit note total (or matches a
  remaining gap on a partially-allocated invoice). Propose a negative
  allocation. Reviewer confirms.

  R7 — Payout batch link (confidence 0.95)
  - Find the txn whose amount equals payout_report.csv net total (2720.73) and
  whose description/counterparty contains "payout" or "stripe". Link
  payout_batches.transaction_id. Per-charge allocations are pre-built from the
  CSV but stay proposed (Tier 2 — reviewer confirms the batch as a whole).

  R8 — Non-AR classifier (noise) (confidence n/a)
  - Keyword rules on description or counterparty_name: salary|payroll
  out|rent|landlord|fee|bank charge|tax authority|refund out, OR amount is
  negative AND no matching invoice. Sets transactions.status = 'unrelated' with
  audit_log entry matcher_marked_unrelated. Reviewer can override.

  Tolerances:
  - Amount equality tolerance: ±2 cents (rounding drift).
  - Overpayment threshold: > 5% AND > €5 → flagged for review; smaller →
  auto-confirmed and a note is written to the audit log.
  - Underpayment: any short payment is treated as a partial; invoice stays
  partially_allocated.

  Idempotency mechanics:
  - For each (txn, invoice) pair the matcher is about to write: upsert on the
  unique index. If a row exists with status != 'proposed', skip (matcher
  invariant from §2). If it exists with status = 'proposed', update
  confidence/rule/amount only if changed; otherwise touch nothing (no spurious
  updated_at churn, no audit-log noise).
  - Tracks per-run stats (rule fire counts, auto-confirmed count, proposed
  count, skipped count) and returns them in MatcherReport. UI shows them after a
   manual run.

  Prepayments (Tier 2): the matcher doesn't try. R4 already requires date >=
  issue_date - 7d, so a txn before issue date naturally falls through and stays
  unmatched. DECISIONS.md notes that a real system would keep a "prepayment
  ledger" and replay matches when invoices are issued.

  What the matcher will NOT do: mutate confirmed or rejected rows, mark a txn
  unrelated if it already has any allocation, or delete allocations. All
  destructive moves are reviewer-only.

⏺ Design — section 5 of 5: Audit, concurrency, API surface, deliverables

  Audit log writes — every state change goes through one helper recordAudit(tx,
  {entity_type, entity_id, action, actor, before, after}) called inside the same
   DB transaction as the change. Never written from the client; the API derives
  actor from a request header (hardcoded reviewer for now). Append-only — no
  UPDATE or DELETE allowed (enforced by Postgres trigger raising EXCLUSION on
  non-INSERT). Indexed on (entity_id, created_at desc) for the panel query.

  Actions written:
  - Matcher: matcher_proposed, matcher_updated, matcher_auto_confirmed,
  matcher_marked_unrelated, matcher_skipped_locked.
  - Reviewer: reviewer_confirmed, reviewer_rejected, reviewer_split,
  reviewer_edited_allocation, reviewer_marked_unrelated,
  reviewer_unmarked_unrelated, reviewer_attached_credit_note,
  reviewer_confirmed_payout_batch.

  before/after are the full row jsonb at change time so the modal can diff them.
   For multi-row changes (e.g. split into 3 allocations), one audit row per
  affected allocation, all sharing a correlation_id jsonb field so the UI can
  group them as one logical action.

  Concurrency (per Q5):
  - transactions.version int. Read endpoints return it. All write endpoints that
   touch a transaction or its allocations require If-Match: <version> header (or
   a version field in body); API does UPDATE transactions SET version = version
  + 1 WHERE id = $1 AND version = $2 RETURNING version inside the same DB tx as
  the change. Zero rows updated → API returns 409 with the current version +
  entity body. UI shows the conflict toast.
  - Matcher uses SELECT … FOR UPDATE SKIP LOCKED per transaction so two parallel
   matcher runs don't double-write. Records matcher_skipped_locked to audit when
   it skips. (Realistically one matcher runs at a time, but this is cheap
  insurance and demonstrates the awareness.)

  API surface (Fastify + zod schemas from shared/):
  - GET    /api/transactions?status=&search=&cursor=
  - GET    /api/transactions/stats
  - GET    /api/transactions/:id (returns txn + version + allocations +
  proposals + payout batch if any)
  - PUT    /api/transactions/:id/allocations body: { allocations: [{invoice_id,
  amount}], version } — replaces the full allocation set as one tx
  - POST   /api/transactions/:id/mark-unrelated body: { version }
  - POST   /api/transactions/:id/unmark-unrelated body: { version }
  - POST   /api/proposals/:id/accept body: { version }
  - POST   /api/proposals/:id/reject body: { version }
  - POST   /api/payout-batches/:id/confirm body: { version, accepted_item_ids:
  [] }
  - GET    /api/invoices?customer_id=&status=&search=
  - GET    /api/audit?entity_id=&limit=
  - POST   /api/matcher/run → returns MatcherReport

  All write endpoints run inside one db.transaction() covering: the change +
  version bump + audit insert. No partial states.
